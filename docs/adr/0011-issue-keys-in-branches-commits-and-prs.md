# ADR 0011: このリポジトリのブランチ名・コミット・PR には、課題キーだけを書いてよい

- **Status**: Accepted
- **Date**: 2026-11-23
- **Deciders**: kazuyukikato
- **Amends**: [ADR 0010](0010-repo-only-config-for-public-repositories.md)（公開のリポジトリでは課題キーを書かずに作業し、扱いは別に決める）
- **Related**: [ADR 0001](0001-plugin-and-project-config.md)（公開のリポジトリなので、社内のプロジェクト名や個別の事情は中身に書かない）

## Context

このリポジトリは公開されているので、AGENTS.md で、社内のプロジェクト名・プロジェクトキー・リポジトリ名などを書かないと決めている。
この決まりに例外は無く、ブランチ名・コミット・PR にも、このリポジトリの課題を管理するプロジェクトの課題キーを書いてこなかった。

一方、`/resolve-issue` は、ブランチ名・コミットの `Refs:`・PR の本文に課題キーを書き、課題の PR を課題キーの検索で探す。
課題キーを書かないと、同じ課題の PR が重ならないかの確かめや、再開のときの PR の探し出しが、課題キーの検索では効かない（ADR 0010 の注意する点）。
GitHub の PR から課題へもたどれない。

課題キーから外に分かるのは、プロジェクトキーと課題の番号くらいである。製品の名前と組織の名前は、このリポジトリですでに公開している。課題の中身は、Issue Tracker にログインしないと読めない。

## Considered Options

- **A. このリポジトリの課題を管理するプロジェクトの課題キーだけを、ブランチ名・コミット・PR に書いてよいことにする。**
- **B. 今のまま書かない。スキルの側に、課題キーを書かないリポジトリのための仕組み（ブランチ名から PR を探す設定など）を足す。**
- **C. 社内の名前を書かない決まりそのものをやめる。**

## Decision

**A を採用する。**

- 書いてよいのは、このリポジトリの課題を管理するプロジェクトの課題キー（`<キー>-<番号>`）だけで、書いてよい場所は、ブランチ名・コミットのメッセージ・PR の件名と本文・PR のコメントに限る。
- 課題の URL（Issue Tracker の接続先が分かる）、ほかのプロジェクトのキー、課題に書いた社内の事情（取引先や、ほかのリポジトリの名前など）は、今までどおり書かない。
- ファイルの中身（文書・例・スキル）には、課題キーも書かない。例は、今までどおり `PROJ-12` のような架空のキーで書く。

B は、スキルと設定の書式を変え、版を上げる必要がある。課題キーを書けば、今のスキルのままで効く。
C は、取引先の名前が入るプロジェクトのキーや接続先の URL まで書けるようになり、公開したものは取り消せない。

## Consequences

良い点:

- このリポジトリでも、`/resolve-issue` が課題キーで PR を探せる。同じ課題の PR が重ならないかを確かめられ、再開のときに PR を見つけられる。
- GitHub の PR やコミットから、課題へたどれる。

注意する点:

- 履歴に課題キーが並ぶので、社内の情報を書いてよいと広く読まれやすい。AGENTS.md の例外の文で、書いてよいものと場所を区切る。
- 外の人には、開けない課題キーが見える。
- これまでの PR とブランチには、課題キーが無い。書き直さない。
- 課題キーを書けないほかの公開のリポジトリのための仕組み（B）は、作っていない。要るときに別に決める。
