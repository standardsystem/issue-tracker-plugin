# ADR 0009: レビューの設定の確かめは、当たったものをまとめて示し、送ってよいという答えを `着手` の印に残す

- **Status**: Accepted
- **Date**: 2026-11-23
- **Deciders**: kazuyukikato
- **Related**: [ADR 0008](0008-check-review-config-before-starting.md)（この ADR が一部を改める）、[ADR 0005](0005-review-model-and-multiple-reviewers.md)

## Context

ADR 0008 で、レビューの設定を着手の前に確かめる節を足した。そのあと、別のエージェントにスキルと書式の文書だけを読ませ、場面ごとの動きを机上で答えさせた。
はっきりした矛盾は無かったが、文面から決められないことが残った。動きに関わるのは次の4つである。

1. 確かめの 1〜3 を、最初に当たったところで止めるのか、全部見てまとめて示すのか。実際に動かした場面では、1 で止まり、直したあとで 3 をもう一度聞いた。
2. 3（Codex に送ってよい範囲）の前提「2 で `codex` を使うと分かったら」が、「使う設定だと分かった」とも「使えると分かった」とも読める。
3. 着手の前に「送ってよい」と答えを受けても、どこにも残らない。セッションをまたいで 5 章へ再開すると、同じ課題でもう一度 `止まった` を残して聞く。
4. 7 章へ再開するときは確かめないが、7.4 は「今の `review.by` の全員」とレビューの印の者を比べる。`format: 1` に一覧を書いたままのとき、その一覧をどう読むかが無い。

ほかに、`## レビュー` に呼び方があるときの確かめ方（端末のコマンドが呼べること、スクリプトへの渡し方、Codex の版の得方）、伝える直し方、`/resolve-issues` で待つ間に進めてよい範囲などの細部が、文面から決まらなかった。

## Decision

- **確かめの 1〜3 は、すべて見て、当たったものをまとめて一度に示す。** 利用者が一度直せば済むようにするためである。
  2・3 は、`review.by` に `codex` が書いてあれば確かめる。1 に当たる一覧でも、2 で使えなかったときも同じである。
  ただし、知らない値（`codx` など）を `codex` に直したときのように、直したことで初めて 2・3 に当たるものは、確かめ直しで分かる。
- **着手の前に受けた「送ってよい」は、その課題の `着手` の印に書く。** 再開して 5 章へ進むときは、`着手` の印か `止まった` の答えにそれがあれば、聞き直さない。
  印には、作業するリポジトリ、表の当たる行、示した呼び方（正本の端末のコマンドなら、そのコマンド）も書く。どれかが今と違えば、利用者が見ていないものを送ることになるので、聞き直す。答えは、その課題とそのリポジトリにだけ効く。
  `/resolve-issues` でリポジトリごとに1回受けた答えも、その答えで着手する課題ごとに `着手` の印に書く。
- **7 章から再開して、今の `review.by` が一覧の書き方に当たるときは、比べずに承認なしのマージの条件を欠くものとする。** 誰が全員かを決められないので、承認を受けるほうに倒す。
- **`## レビュー` に呼び方があるときは、レビューを動かさずに確かめられることだけを確かめる。**
  端末のコマンドは、そのプログラムが見つかること（`command -v`）。スクリプトは、既定のブランチにあることと、作業ツリー・依頼文・結果の渡し方が分かること（`## レビュー` か、スクリプトの文面）。渡し方が分からなければ、5 章で動かせないので、使えないものとする。
  スクリプトは `--help` でも動かさない。引数を無視してレビューを始めるスクリプトでは、範囲を確かめる前に外へ送りうるためである。
  Codex の版は、`## レビュー` に決め方があればそれで、呼び方が版を固定していればその版とし、どちらでもなく手元の `codex` を使うときは `codex --version` で得る。どちらでも得られなければ、レビューのコメントに「版は分からない」と書く。
- **送ってよいと答えただけのときは、設定を読み直さない。** 設定のファイルかスクリプトを直したと答えたときだけ、0 章の 3 と 6 をやり直す。
- **`/resolve-issues` は、レビューを待つ間に、次の課題の PR を出すところ（4 章）まで進めてよい。** 待っている課題のブランチには、結果が返るまでコミットも push もしない。

## 検討した代替案

- **最初に当たったところで止める。** 文面の素直な読みだが、設定の誤りが2つあると、利用者は2回止められる。確かめ 1〜3 はどれも着手の前で、ほかの結果に左右されずに見られる。
- **3 は、2 で `codex` を使えると分かったときだけ確かめる。** `codex` を入れる前に、送ってよいかを聞かずに済む。しかし、入れたあとでもう一度止まることになり、上と同じく利用者の手間が増える。
- **「送ってよい」をセッションの中だけに留める（0.9.0 の文面どおり）。** 印に残さなければ、再開するたびに聞く。外に送るものの許しは、記録に残るほうが確かめやすい。課題のコメントはプロジェクトの誰でも読めるが、残すのは許しを受けたことだけで、秘密は含まない。
- **送ってよいという答えを、リポジトリの設定に書く。** スキルは頼まれなければ設定を書き換えない（ADR 0008）。設定に書くことは、今までどおり利用者に勧める。
- **7 章からの再開でも、節をすべて確かめて止まる。** レビューをもう使わない段階で `codex` の有無を聞くことになる。比べられないときに承認を受ければ、マージの安全は保てる。

## Consequences

- 設定の誤りが複数あっても、利用者は一度の答えで直せる。
- 着手の前に「送ってよい」と答えた課題は、セッションをまたいで再開しても聞かれない。新しい課題では、今までどおりセッションごとに1回聞かれる。
- `## レビュー` にスクリプトの呼び方だけを書き、渡し方がどこにも無いリポジトリは、着手の前に止まるようになる。
- `format: 1` に一覧を書いたまま 7 章から再開すると、マージの直前に承認を求められる。
- 設定のファイルの書式の番号と、コメントの印の文言は変えない。`着手` の印の本文に書くことが1つ増える。
