# ADR 0001: 課題を解決するスキルをプラグインとして配り、プロジェクトの違いは設定のファイルに書く

- **Status**: Accepted
- **Date**: 2026-11-06
- **Deciders**: kazuyukikato
- **Related**: [issue-workflow-format.md](../issue-workflow-format.md)、[comment-markers.md](../comment-markers.md)
- **Amended by**: [ADR 0002](0002-no-bundled-mcp-server.md)（MCP サーバーの接続の設定はプラグインに含めない）

## Context

STANDARD Issue Tracker の課題を、Claude Code が着手の確認から完了まで解決するスキルを、ある1つのプロジェクトで作って使ってきた。

- `/resolve-issue <課題キー>`: 課題を1件、着手の確認 → 処理中 → 実装と確認 → PR → レビューと対応（最大3回） → マージ → 公開 → 本番で確認 → 完了、の手順で解決する
- `/resolve-issues [課題キー…]`: 複数件を `/resolve-issue` の手順で1件ずつ解決し、最後に結果をまとめる

Issue Tracker を使うほかのプロジェクトでも使いたい。しかし今の中身には、そのプロジェクトに固有のことが混ざっている。

- プロジェクトキーと、カテゴリーからリポジトリを決める表
- 状態の名前（「処理中」「処理済み」「完了」）
- 確認・公開のコマンド、毎回利用者に確かめる操作
- レビューに使う外部のモデル（Codex）の呼び方と版、送ってよい範囲
- マージの方法

Issue Tracker のサーバーは非公開で、デプロイできる人は限る。一方、スキルを使う人（Issue Tracker の利用者）は比較的広い。

## Considered Options

配り方:

- **A. Claude Code のプラグインにして、専用の公開リポジトリから配る**
- **B. Issue Tracker の MCP サーバーの prompts として出す**
- **C. テンプレートを文書に置き、各リポジトリに写してもらう**

公開と本番での確認（手順 8〜9）の扱い:

- **D. 共通の手順に骨組みを残し、公開の型と中身を設定で埋める**
- **E. 設定に公開の節があるときだけ動く、追加の段階にする**

版の上げ方:

- **F. 利用者は常に最新版を使う**
- **G. 利用者が版を固定できる（タグで出し、使う版を指定する）**

## Decision

**A・D・F を採用する。**

### 配り方

- Issue Tracker 専用のプラグインにし、専用の公開リポジトリに、マーケットプレイスの定義とプラグインを置く。
  プラグインは利用者のためのものなので、非公開のサーバーのリポジトリとは分ける。
- プラグインには、スキル2つを含める。
  MCP サーバー `issue-tracker` への接続の設定も含めるとしていたが、[ADR 0002](0002-no-bundled-mcp-server.md) で含めないことに変えた。
  公開のリポジトリなので、接続先・社内のプロジェクト名・個別の事情は中身に書かない。
- 正本はこのリポジトリだけとする。スキルを作ったプロジェクトも利用者の側に回り、手元のコピーは消す。
- B は採らない。スキルの中身は、git の作業ツリー・`gh`・バックグラウンドでの実行・利用者への確認など、利用者の手元で行う作業がほとんどである。
  課題の操作だけを受け持つサーバーが、手元の作業手順まで抱えることになり、手順を直すたびにサーバーの公開も要る。
- C は、写したあとの同期ができないので採らない。導入の手順を書いた文書は、プラグインの付属として置く。

### 共通の手順と、プロジェクトの設定を分ける

- プロジェクトごとの違いは、各リポジトリの `.agents/issue-workflow.md` に書く。
  `AGENTS.md` には、そのファイルを指す1行だけを置く。`AGENTS.md` を短く保ちつつ、どのエージェントからも読めるようにするためである。
  `.claude/` は Claude Code 専用なので使わない。
- 設定に書くこと: プロジェクトキー、カテゴリーとリポジトリの対応、状態の役割と名前の対応、確認のコマンド、マージの方法、レビューの方法、公開と確認、利用者に必ず確かめること。
- YAML に書式の番号（`format: 1`）を書く。スキルは古い書式を見つけたら、書き換えを提案する。
- 設定のファイルが無いリポジトリでは、スキルが `list_statuses` などを読んで案を作り、ファイルを書くことを提案する。
- YAML（スキルが分岐に使う値）と Markdown（手順や注意の文章）に分け、プロジェクトの層とリポジトリの層を分ける。
  複数のリポジトリにまたがるプロジェクトでは、プロジェクトの層を正本のリポジトリに1か所だけ書き、ほかのリポジトリからは `definedIn` で指す。
  正本は `gh api` で GitHub から読む。書式の詳細は [issue-workflow-format.md](../issue-workflow-format.md)。

### レビュー

- レビューは任意の段階とし、既定では Claude の別のエージェントにさせる。Codex などほかのモデルは、設定で選ぶ。
- 重大度（P0〜P3）、指摘の仕分け、止まる条件（P0・P1 が 0 件で、P2 はすべて直したか理由を書いた）、最大3回は、レビューする者によらず共通とする。
- Codex に頼む場合も、Codex 側のスキルには頼らず、依頼文の型をプラグインに含める。

### 公開と本番での確認（D）

- 共通の手順に、次の決まりを残す。
  - マージしただけでは完了にしない。
  - 公開は、利用者の指示があるときだけ行う。
  - 公開は、きれいな作業ツリーから行う。
  - 確かめられなければ、完了にせず利用者に頼む。
- 公開の型（なし・自動・手動・リリース・外部の審査）と、コマンド・待ち方・確かめ方は設定に書く。
- 設定に公開の型が無いときは、型が分からないものとして扱い、着手の前に利用者に聞く。
  「公開: なし」と明記してあれば、マージした時点で完了にする。
- マージと公開は、その直前に毎回、利用者の承認を受ける。スキルの呼び出しや「解決して」という依頼は、承認にならない。
  最初に「マージまで任せる」と言われたら承認を省く、という扱いは 0.1.0 では採らない。
  任されたかどうかの判定と、その例外（自動の型、毎回確かめる操作）の組み合わせから、承認なしにマージや公開が起きる穴がレビューで繰り返し見つかったためである。
  まとめて任せる仕組みは、必要になったら `/resolve-issues` で改めて決める。
- 「自動」の型（main に入ると公開される）では、マージの承認が公開の承認を兼ねることを、利用者に明示して聞く。
- 「リリース」の型では、「次のリリース待ち」で止める。リリースを出すことは、このプラグインの範囲の外とする。
- E は採らない。設定を書き忘れたとき、マージした時点で完了にしてしまい、上の決まりがいちばん起こりやすい場面で効かなくなるためである。

### 状態とコメント

- 状態は、役割（着手 / main に入ったが確かめていない / 完了）と、プロジェクトでの名前の対応を設定に書く。
  完了の役割は、`list_statuses` の完了扱いの印からも決められる。
- 「main に入ったが確かめていない」に当たる状態が無いプロジェクトでは、「処理中」のままにし、コメントで区別する。
- 課題に残すコメントは、先頭に決まった印（`[resolve-issue] PR を作成`・`[resolve-issue] 確認待ち` など）を付ける。印の一覧は [comment-markers.md](../comment-markers.md) に載せる。
- 着手の確認では、最新の印付きのコメントで状態を見分ける。
  「確認待ち」「リリース待ち」の課題は、別の人が作業中とはみなさず、続きから再開できるものとして扱う。
  印付きのコメントが無い「処理中」の課題は、これまでどおり作業中かもしれないとみなす。
- 「着手」「PR を作成」などの印のまま、セッションが途中で終わって放置された課題も、作業中とみなす。
  最後のコメントの日時と PR の状態を添えて利用者に聞き、続きから再開するか外すかを選んでもらう。
  時間で自動に再開すると、別の人が長く作業している課題を横取りするおそれがあるためである。
- `/resolve-issues` は、待っている課題を新しく着手する候補に混ぜず、「確認を再開できる課題」として別に示す。

### 版の上げ方（F）とサーバーとの対応

- 利用者は常に最新版を使う。版の番号（semver）とタグは付け、変更を CHANGELOG に書く。
- サーバーが求めるプラグインの最も古い版は、Issue Tracker の MCP サーバーの instructions に書く
  （例: 「issue-tracker プラグインのスキルは、版 1.2.0 以上で使ってください。」）。
  instructions はサーバーのコードにあるのでデプロイとずれず、接続のたびにエージェントへ届き、参加しているプロジェクトによらず読める。
- 各 `SKILL.md` に自分の版を書く。CI で `plugin.json` の版と一致することを検査する。
  スキルは最初に、instructions の版と自分の版を比べる。古ければ利用者に更新を勧め、続けるかを聞く。
- サーバーの版の番号は基準にしない。利用者はサーバーの版を選べず、変えられるのはプラグインの版だけだからである。
- Issue Tracker の Wiki には置かない。Wiki はプロジェクトの参加者しか読めず、手作業の更新はデプロイとずれるためである。
- G は採らない。古い版を MCP の側で支え続ける費用に見合う利点が、今はない。版の番号とタグを付けておくので、必要になれば移れる。

## Consequences

良い点:

- 直したものが一度に全員へ届き、サポートする版が1つで済む。
- プロジェクトごとの違いが1つのファイルにまとまり、どのエージェントからも読める。
- 公開と確認の決まりが、設定を書き忘れたプロジェクトでも効く。
- 印付きのコメントで、止まった課題を続きから再開できる。

注意する点:

- 誤った変更も、全員に一度に届く。CHANGELOG と版の番号を必ず更新する。
- 壊れる変更は、新旧どちらのサーバーでも動く版のプラグインを先に出してから、サーバーを変えて最低の版を上げる。順番を逆にしない。
- MCP のツールや引数は、すぐには消さない。名前を変えるときは、古い名前もしばらく受け付ける。
- 最低の版の案内を足すため、Issue Tracker 本体にも小さな変更（instructions に1行と、そのテスト）が要る。
- リリースの型のプロジェクトでは、課題が「リリース待ち」のまま残る。リリースを出したあとの確認は、`/resolve-issue` を再び呼んで続きから行う。
