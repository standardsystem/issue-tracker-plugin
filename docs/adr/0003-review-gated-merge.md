# ADR 0003: レビューで止まる条件を満たした PR は承認なしでマージし、まとめて任せる仕組みは作らない

- **Status**: Accepted
- **Date**: 2026-11-08
- **Deciders**: kazuyukikato
- **Amends**: [ADR 0001](0001-plugin-and-project-config.md)（マージと公開は、その直前に毎回、利用者の承認を受ける）
- **Related**: [issue-workflow-format.md](../issue-workflow-format.md)、[comment-markers.md](../comment-markers.md)

## Context

0.1.0 の `/resolve-issue` は、マージと公開の直前に毎回、利用者の承認を受ける（ADR 0001）。
「最初にマージまで任せる」と言われたら承認を省く、という扱いは、任されたかの判定とその例外の組み合わせから穴が見つかったため採らなかった。

実際のプロジェクトで使ってみると、1件あたりの承認はマージと公開の2回で、1件なら負担は小さかった。
一方、レビューで止まる条件は、マージしてよいかを確かめるための条件である。その条件を満たした PR に、さらにマージの承認を求めると、同じことを2回確かめることになる。
利用者は、レビューで止まる条件を満たした PR は承認なしでマージしてよい、と決めた。
また、複数件を順に解決する `/resolve-issues` では、課題ごとにマージの承認で待つと、利用者が席を外している間に進まない。

`/resolve-issues` の元になったスキルは、最初に「マージ・公開を任せるか」をまとめて聞き、任されたら途中で聞き直さない、としていた。

## Considered Options

マージの承認:

- **A. 毎回受ける（0.1.0 のまま）**
- **B. 決まった条件をすべて満たすときだけ省く。条件はスキルが自分で確かめられるものに限る**
- **C. 利用者が「任せる」と言ったら省く**

`/resolve-issues` の承認:

- **D. 最初にまとめて任せてもらい、途中で聞き直さない**
- **E. まとめて任せない。承認が要るところで課題を止めて次へ進み、最後にまとめて求める**

## Decision

**B と E を採用する。**

### マージ（B）

承認を受けずにマージするのは、次をすべて満たすときだけとする。1つでも欠ければ、マージの直前に承認を受ける。

- レビューを1回以上終え、最後の回の正しい P0・P1 が 0 件だった。レビューをしない設定、レビューを飛ばしたとき、3回目以降に止まってから利用者が「このまま進む」を選んだときは欠ける。
- PR の CI にチェックがあり、成功した。
- マージしても公開されない。公開の型が `auto` か、分からないときは欠ける。マージの承認が公開の承認を兼ねるためである。
- 設定の `## 毎回確かめること` に、そのマージが当たらない。

条件は、どれも課題の印、PR のコメント、CI、設定からスキルが確かめられる。利用者の言葉の解釈に頼らないので、C で見つかった穴（何を任されたかの判定の誤り）が起きない。
C は採らない。理由は ADR 0001 のとおりである。

公開は、今までどおり毎回その直前に承認を受ける。マージは PR を戻せば取り消せるが、公開は利用者に届いてしまい、取り消せないことが多いためである。

マージを毎回確かめたいプロジェクトは、`## 毎回確かめること` に「すべてのマージ」と書く。書式に新しい項目は足さない。

### `/resolve-issues`（E）

- 最初に任せてもらうことはしない。「マージ・公開まで任せる」と言われても、承認にしない。
- 承認や利用者の判断が要るところに来た課題は、`/resolve-issue` と同じ印（`止まった`・`確認待ち`・`リリース待ち`）を残して止め、次の課題へ進む。
- すべての課題を終えたら、止めた課題の承認と判断をまとめて求める。承認を受けた課題は、`/resolve-issue` の再開の手順で続ける。
- D は採らない。任された範囲を記録する場所と、任されても聞き直す例外（`auto` の型、毎回確かめる操作）が要り、ADR 0001 で避けた穴がそのまま戻る。
  B でマージの承認の多くが要らなくなるので、最後にまとめて求める承認は、主に公開と、条件を欠いたマージになる。

## Consequences

良い点:

- レビューを通った PR は、利用者を待たずにマージまで進む。
- `/resolve-issues` で、利用者がいない間も、承認の要らない課題は先に進む。
- 承認の要否を、スキルが確かめられる事実だけで決めるので、判定が揺れない。

注意する点:

- レビューの最後の回のあとに push した修正（P2 の修正など）は、再レビューを受けずにマージされる。7 章の確認で、そのコミットがすべて自分の push であることは確かめる。
- 公開の型を書き忘れると、マージの承認が毎回要る。省略は「分からない」として扱うので、安全な側に倒れる。
- `マージ` の印に、承認を受けたかを書く。あとで、承認なしでマージした PR を見分けられるようにするためである。
