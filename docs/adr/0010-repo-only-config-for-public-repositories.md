# ADR 0010: 公開のリポジトリには、リポジトリの層だけの設定を置き、正本からたどる

- **Status**: Accepted
- **Date**: 2026-11-23
- **Deciders**: kazuyukikato
- **Related**: [ADR 0001](0001-plugin-and-project-config.md)（設定のファイルを、プロジェクトの層とリポジトリの層に分けた）、[ADR 0004](0004-inherit-review-section.md)（正本の Markdown の節の受け継ぎ）

## Context

複数のリポジトリにまたがるプロジェクトでは、正本のリポジトリにプロジェクトの層を書き、ほかのリポジトリには `project.definedIn` で正本の場所を書いていた。
`project.key` は必須で、`definedIn` には正本の `owner/repo` を書く。

ところが、プロジェクトのリポジトリの中に、公開のリポジトリがあることがある（利用者に配るプラグインや SDK など）。
公開のリポジトリには、社内のプロジェクトキーや、非公開の正本のリポジトリ名を書けない。
そのため、そのリポジトリには設定のファイルを置けず、課題を解決するたびに、確認のコマンド・マージの方法・公開の型を前の回から推し量るか、利用者に聞いていた。

また、`project.repositories` はカテゴリーとリポジトリを対応させるが、カテゴリーが機能の区分で、ほとんどの課題が1つのリポジトリに向かうプロジェクトでは、カテゴリーの無い課題や、表に無いカテゴリーの課題の行き先が決まっていなかった。

## Considered Options

- **A. `project` を書かない「リポジトリの層だけのファイル」を認め、正本の `repositories` からだけたどる。**
- **B. 公開のリポジトリにも `definedIn` を書き、正本の場所だけは出してよいことにする。**
- **C. 公開のリポジトリの設定を、正本のファイルの中に書く（リポジトリごとの `repo` を正本に並べる）。**
- **D. Git で管理しないローカルのファイル（`.agents/issue-workflow.local.md` など）に、プロジェクトの層の場所を書く。**

## Decision

**A を採用する。**

- `project` の無いファイルを、リポジトリの層だけのファイルとして読む。`repo.category` も書かない（カテゴリーの名前も社内の事情になりうるため）。
- スキルは、正本からカテゴリーでたどったときにだけ、このファイルの `repo` と Markdown の節を読む。
  `repo` の値の決め方と、正本の Markdown の節の受け継ぎ（ADR 0004）は、`definedIn` を書いたリポジトリと同じにする。
- このリポジトリで作業を始めたときは、プロジェクトの層を見つけられないので、正本のリポジトリで始め直すよう伝えて止まる。
  正本の場所を推し量らない。設定が無いときとして扱って案を作ることもしない。プロジェクトキーを書く案を公開のリポジトリに出さないためである。
- 正本に `project.defaultRepository` を足す。`repositories` に無いカテゴリーの課題と、カテゴリーの無い課題は、そのリポジトリで解決する。省略すれば、今までどおり利用者に聞く。
  `defaultRepository` のリポジトリでは、`repo.category` を省略できる。

B は、非公開のリポジトリ名を出すことになり、公開のリポジトリに社内の名前を書かない決まりと合わない。
C は、リポジトリの確認や公開の手順が、そのリポジトリから離れた場所に書かれ、そのリポジトリの変更と一緒に直せない。
D は、clone ごとに書く必要があり、書き忘れると黙って効かない。ADR 0001 の、手元の clone の場所に左右されない読み方とも合わない。

`defaultRepository` を、`repositories` に無いものは正本で解決する、という暗黙の決まりにしなかったのは、カテゴリーをリポジトリごとに付けるプロジェクト（例 2）で、付け忘れた課題が黙って正本に向かうのを防ぐためである。

## Consequences

良い点:

- 公開のリポジトリにも、確認のコマンド・マージの方法・公開の型・確かめ方を置ける。社内の名前は出ない。
- リポジトリの確認や公開の手順を、そのリポジトリの変更と一緒に直せる。
- カテゴリーを機能の区分に使うプロジェクトでも、`defaultRepository` で、カテゴリーの無い課題の行き先を決められる。

注意する点:

- リポジトリの層だけのファイルのリポジトリでは、`/resolve-issue` を始められない。正本で始める。
- 正本の `## レビュー` と `## 毎回確かめること` は、このリポジトリにも効く。正本の `## レビュー` の中身は、レビューの依頼文と、6 章のレビューのコメント（Codex の版と呼び方）を通して、公開のリポジトリの PR のコメントに写りうる。正本の `## レビュー` に社内の事情を書かない。
- スキルは、ブランチ名・コミット・PR の本文に課題キーを書く。公開のリポジトリでは、その決まり（AGENTS.md など）が優先し、課題キーを書かずに作業する。そのとき、課題の PR は課題キーの検索では見つからず、`着手` の印に書いたブランチからたどる。これを設定や手順で扱うかは、別に決める。
- 0.10.0 までのスキルは、リポジトリの層だけのファイルで始めると、`project.key` が無いことに気づかずに進むか、設定が無いものとして案を作りうる。書式の番号は、今あるファイルがそのまま読めるので 1 のままにし、CHANGELOG に書く。
