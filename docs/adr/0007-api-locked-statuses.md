# ADR 0007: API キーでは変えられない状態への変更は、利用者に画面で変えてもらう

- **Status**: Accepted
- **Date**: 2026-11-20
- **Deciders**: kazuyukikato
- **Related**: [comment-markers.md](../comment-markers.md)、[ADR 0003](0003-review-gated-merge.md)、[ADR 0006](0006-reserve-issue-while-working.md)

## Context

Issue Tracker のサーバーに、状態ごとの設定「API キーではこの状態にできない」が入った。振る舞いは次のとおりである。

- 付いた状態へ、API キー（REST・MCP）から課題を変えると、エラーになる。エラー文は、人が画面で変える必要があることを伝える。
- 縛るのは「その状態へ変える」ことだけである。付いた状態から別の状態へ戻すことと、今と同じ状態を指定することはできる。
- `list_statuses` は、状態ごとに `apiLocked` を返す。エージェントが、変えられない状態を事前に避けられるようにするためである。
- 設定を変えられるのは、画面からだけである。

この設定は、「完了は人が決める」のような決まりを、エージェントへの指示ではなく、サーバーで守らせるためにある。

スキルは、課題の状態を3回変える。着手（2 章）、マージ済み（8・9 章で止めるとき）、完了（9 章）である。
0.7.0 までは、どれかが上のエラーになると、スキルはそこで止まるだけで、利用者に何を頼むか、どの印を残すか、どう再開するかが決まっていなかった。
`update_issue` は、エラーになると同じ呼び出しの `comment` も残さないので、`着手`・`完了` の印も残らなかった。

## Decision

- **0 章で `list_statuses` の `apiLocked` を見て、付いた状態には `update_issue` で変えようとしない。** エラーを待たずに、決めた手順に入る。
  見たあとで設定が変わることがあるので、`update_issue` がそのエラーになったときも、同じ手順に入る。`apiLocked` を返さない古いサーバーでは、今までどおりに進む。
- **完了の状態に付いていれば、すべて確かめたあとで `止まった` を残して止まり、画面で完了に変えるよう頼む。** 新しい印は足さない。
  マージの承認を待つときと同じく、「利用者が決めることを待つ」ので、同じ印を使う。本文には、`完了` の印に書く「確かめたこと」も書く。
  状態が完了になったことを `get_issue` で確かめたら、`完了` の印を残す。利用者の「変えた」という答えだけでは進めず、課題を読んで確かめる。
- **着手の状態に付いていれば、着手の前に頼む。** 状態が着手になったことを確かめるまで、予約もブランチも印も作らない。
  着手を人に限るプロジェクトは、どの課題を始めるかを人が決めたい。スキルが先に作業を始めては、その決まりを破る。
  `resolve-issues` は、順番を示すときにまとめて頼む。
- **マージ済みの状態に付いていても、止まらない。** 状態は着手のままにし、8・9 章で残す印の本文にそのことを書いて、あわせて頼む。
  マージ済みの状態は、スキルが止まるときにだけ付ける。そのときは、もう利用者の答えを待っている。再開は印で決まり、状態は見ないので、変わらなくても続きに困らない。
  設定に `merged` が無いプロジェクト（着手のまま、印で区別する）と同じ扱いである。
- **設定を避けない。** 状態の設定を外す、ほかの状態で代える、ほかの API キーや経路を使う、などをしない。利用者に頼まれても、状態は利用者が画面で変える。

## 検討した代替案

- **新しい印 `承認待ち` を足す。** 何を待っているかは印の名前で分かりやすくなるが、印を足すと、古い版のスキルがその印を知らずに、1つ前の印（`マージ` など）から作業中とみなす。
  `止まった` の本文に「決めてほしいこと」を書けば足りる。
- **`確認待ち` に、残っている段階「状態の変更」を足す。** `確認待ち` は、公開か本番での確認が残っていることを表す。完了にできないときは、確認はすべて終わっているので、意味がずれる。
- **`完了` の印を先に残し、状態だけを利用者に頼む。** 印が `完了` で状態が完了扱いでない課題は、開き直された課題とみなす決まりと区別できない。
- **着手の状態に付いていても、`着手` の印だけを残して作業を始め、状態はあとで頼む。** 手間は減るが、着手を人が決めるという設定の目的に反する。
- **事前に見ずに、エラーだけで決める。** `update_issue` を1回無駄に呼ぶだけでなく、着手では、ブランチを切ったあとで初めて分かる。事前に見れば、何も作る前に頼める。

## Consequences

- 完了の状態に付けたプロジェクトでは、スキルだけでは課題は完了にならない。`resolve-issues` では、先行課題が完了にならないので、同じ回では後続課題に着手しない。
- 利用者が画面で完了にしたあと、スキルを呼ばなければ、最新の印は `止まった` のまま残る。状態は完了なので、スキルは着手しない。次に呼んだときに、`完了` の印を足す。
- マージ済みの状態に付けたプロジェクトでは、利用者が変えるまで、マージしたあとの課題も着手の状態のまま見える。区別は印でつく。
- `list_statuses` を、プロジェクトごとに1回呼ぶ。
