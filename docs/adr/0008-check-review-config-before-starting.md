# ADR 0008: レビューの設定は着手の前に確かめ、Codex に送ってよい範囲が分からなければ利用者に確かめる

- **Status**: Accepted
- **Date**: 2026-11-21
- **Deciders**: kazuyukikato
- **Related**: [ADR 0001](0001-plugin-and-project-config.md)、[ADR 0004](0004-inherit-review-section.md)（この ADR が一部を改める）、[ADR 0005](0005-review-model-and-multiple-reviewers.md)
- **Amended by**: [ADR 0009](0009-show-all-review-config-problems-at-once.md)（確かめの 1〜3 はすべて見てまとめて示す。送ってよいという答えを `着手` の印に残す）、[ADR 0012](0012-ask-when-pr-changes-review-script.md)（PR がレビューのスクリプトを変えたときは、聞かずに従わず、差分を示して確かめる）、[ADR 0013](0013-read-settings-from-default-branch.md)（手元のリポジトリの設定も、既定のブランチのものを読む。直しをすぐ読むのは、既定のブランチの作業ツリーの未コミットの変更だけ）

## Context

ADR 0005 で、`review.by` に一覧を書けるようにした。そのあと、別のエージェントにスキルと書式の文書だけを読ませ、設定ごとの動きを机上で答えさせた。
動きは文面どおりに決まったが、次のことは文面から決められなかった。

1. 一覧の書き方の誤り（`format: 1` に一覧、`none`、重複）で止まったとき、スキルは「設定の修正を求める」としか書いていない。何に直すよう勧めるか、直したあと同じセッションで続けてよいかが無い。
2. `codex` コマンドが使えるかを、着手の前に確かめる文が無い。使えなければ、実装して PR を出したあとの 5 章で初めて失敗する。
3. 書式は、Codex に送ってよい範囲を `## レビュー` に書くとしている。しかし、書いてないときに、スキルが既定のコマンドでそのまま動かしてよいかが無い。
   既定のコマンドは、PR の head を取り出した作業ツリーを Codex に渡す。依頼文には、課題の件名と「やること」も入る。
   作業ツリーは元のリポジトリの履歴を共有するので、Codex は履歴（消したファイル、ほかのブランチ）も読みうる。
4. 「数分かかるので、バックグラウンドで動かす」が、Codex と、複数の者を並べたときにだけ書いてある。Claude のエージェント一人のときにも当たるのかが分からない。

3 は、外部のサービスに送る情報に関わる。`review.by` は正本の `project.defaults` から受け継げるので、外に出せないファイルを含むリポジトリが、誰もそのリポジトリのことを考えないまま `codex` になりうる。

## Decision

- **レビューの設定は、着手の前に、1つの節でまとめて確かめる。** 一覧の書き方、`codex` を使えるか、Codex に送ってよい範囲の順に見る。
  当たれば 2 章の 1 へ進まない。着手の前なので、課題の状態も印も予約も変えない。
  確かめるのは、1 章で着手すると決まったあと（2 章の前置き）と、再開して 5 章へ進むときだけにする。着手しない課題や、レビューをもう使わない再開（7 章から先）で、止めたり聞いたりしないためである。
- **一覧の書き方の誤りには、勧める直し方と、ほかの直し方を示す。** 選ぶのは利用者である。
  - `format` が 2 でない: 2 にすることを勧める。一覧を書いた人は、複数の者を並べたかったと考えるためである。要素が1つなら、1つの値で書く道も示す。
  - `none` がある: 一覧から外すことを勧める。者を並べた人は、レビューさせたかったと考えるためである。レビューしないのなら、`by: none` と書く。
  - 重複: 重なった分を外す。モデルの違う Claude を並べたかったのなら、`review.model` か `codex` を案内する。
  - 空・知らない値: 者を書く、書き間違いを直す。
- **設定のファイルは利用者が直し、直したあとは同じセッションで続けてよい。** スキルは設定を読み直して、節を初めから確かめ直す。
  正本のファイルは GitHub の既定のブランチから読むので、正本を直したときは、既定のブランチに入ってから続ける。
  スキルが頼まれずに書き換えないのは、設定がレビューとマージの条件を決めるためである。
- **`codex` を使えるかは、着手の前に確かめる。** `## レビュー` に呼び方があれば、そのコマンドかスクリプトがあること。無ければ、`codex --version` が動くこと。
  使えなければ着手しない。`codex` の代わりに `claude` でレビューしない（ADR 0005 の `review.model` と同じ理由）。ログインの状態までは確かめない。
- **Codex に送ってよい範囲が分からなければ、着手の前に利用者に確かめる。** `## レビュー` に呼び方があれば、範囲はその呼び方が決めるものとして従う。
  呼び方が無く、全体を送ってよいと書いてあれば、既定のコマンドで動かす。呼び方が無く、全体より狭い範囲が書いてあれば、既定のコマンドでは守れないので止まる。
  全体を送ってよいと読むのは、作業するリポジトリの節に書いてあるか、正本の節にどのリポジトリのことかを明記してあるときだけにする。
  範囲を絞る決まりと呼び方は正本から受け継ぐが（ADR 0004）、広げる許しは、対象のはっきりしたものに限る。正本のリポジトリのつもりで書いた許しが、プロジェクト全体の許しにならないようにするためである。
  正本の節にだけある端末のコマンドの呼び方（版を固定した `codex exec …` など）も、同じに扱う。その呼び方で動かすが、範囲を絞るとは限らないので、全体を送ってよいと読めなければ確かめる。
  作業するリポジトリの中のスクリプトを呼ぶ呼び方は、そのリポジトリにスクリプトを置いた人が範囲を決めているので、聞かずに従う。
  呼び方も範囲も無ければ、送るものを示して確かめる。答えは、そのセッションの、そのリポジトリの課題にだけ効く。次から聞かれないよう、`## レビュー` に書くことを勧める。
- **バックグラウンドで動かしてよいのは、どの者でも同じにする。** `claude` でも `codex` でも、一人でも複数でも、手段があればバックグラウンドで動かしてよく、無ければ前面で待つ。
  どちらでも、全員の結果が返るまで 6 章へ進まず、ブランチに push しない。

## 検討した代替案

- **範囲が書いてなければ、聞かずに既定のコマンドで動かす。** `review.by: codex` と書いたことを、送ってよいという意思とみなす案である。手間は無いが、`project.defaults` から受け継いだだけのリポジトリでは、その意思があったとは言えない。
  外に送ったものは取り消せないので、聞くほうに倒す。聞かれたくないリポジトリは、1行書けば済む。
- **範囲が書いてなければ、いつも止まり、書くまで進まない。** 確実だが、設定を直して PR を出すまで課題に着手できない。その場の答えで進めるようにし、書くことは勧めるだけにする。
- **5 章の直前に確かめる。** 着手のあとなので、`止まった` の印が要り、実装が無駄になることもある。着手の前に分かることは、着手の前に確かめる。
- **スキルが設定を直す。** 直し方が1つに決まらない（`none` を外すのか、`none` だけにするのか）。選ぶのは利用者である。
- **`codex` が使えなければ、`claude` で代える。** 一覧で2人を並べたのに1人分のレビューで承認なしのマージに進むことになり、ADR 0005 の考えに反する。

## Consequences

- `## レビュー` に呼び方も範囲も書かずに `codex` を使っていたリポジトリは、セッションごとに1回、送ってよいかを聞かれるようになる。そのリポジトリの `## レビュー` に呼び方か範囲を書けば、聞かれない。
- 正本の設定に誤りがあるときは、直しが正本の既定のブランチに入るまで、そのプロジェクトの課題に着手できない。
- スキルが利用者に示すのは、既定のコマンドで渡すものと、Codex が読みうるもの（履歴）までである。Codex が読む範囲そのものは、スキルでは絞れない。絞るには、呼び方を書く。
- 再開して 5 章へ進むときに当たると、もう着手しているので、`止まった` を残してから聞く。
- `codex` のログインが切れているなどの失敗は、今までどおり 5 章で分かる。
- 設定のファイルの書式の番号と、コメントの印は変えない。
