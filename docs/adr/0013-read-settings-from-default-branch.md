# ADR 0013: 手元のリポジトリの設定のファイルは、既定のブランチのものを読む

- **Status**: Accepted
- **Date**: 2026-11-23
- **Deciders**: kazuyukikato
- **Related**: [ADR 0001](0001-plugin-and-project-config.md)（プロジェクトの違いを設定のファイルに書く）、[ADR 0003](0003-review-gated-merge.md)（承認なしでマージする条件）・[ADR 0008](0008-check-review-config-before-starting.md)・[ADR 0012](0012-ask-when-pr-changes-review-script.md)（この ADR が、3 つの一部を改める）

## Context

スキルは、作業を始めたリポジトリと、作業するリポジトリの `.agents/issue-workflow.md` を、手元のフォルダーから読んでいた。`definedIn` で指した正本だけは、GitHub の既定のブランチから読む。

手元のフォルダーが、いつも既定のブランチの最新とは限らない。

1. スキルは、作業ツリーがきれいなら、利用者の作業ツリーで課題のブランチに切り替える。再開のときは、手元のファイルが課題のブランチのものになる。
   課題の変更が設定のファイルを変えていると、その変更が、既定のブランチに入る前から、その課題の手順に効く。
   `## レビュー` に「全体を送ってよい」と足す変更なら、利用者が確かめないまま Codex へ送られる。`review.by`・`deploy.type`・`## 毎回確かめること` の変更なら、レビューやマージの承認の条件が、変えたあとの値で決まる。
2. ほかのセッションが、同じ作業ツリーで別の課題のブランチに切り替えていることがある。その課題の変更が、関係のない課題の手順に効く。
3. 隣のフォルダーの clone が、既定のブランチより遅れていることがある。古い設定か、設定が無いものとして読まれる。

設定のファイルは、レビューする者、外へ送ってよい範囲、マージと公開の条件を決める。ADR 0012 は、PR がレビューのスクリプトを変えたときのことを決めたが、設定のファイルそのものを変えたときのことは決めていなかった。

## Decision

- **手元のリポジトリの設定のファイルは、既定のブランチ（`git fetch origin` のあとの origin/main）のものを読む。** 作業を始めたリポジトリと、作業するリポジトリの両方に当てる。0 章でも、あとで読み直すときも同じにする。
  課題のブランチで変えた設定は、既定のブランチに入るまで、どの課題の手順にも効かない。設定を変える課題も、変える前の設定で解決する。
- **手元の作業ツリーのファイルを読むのは、次のすべてに当たるときだけにする。** 作業ツリーが既定のブランチをチェックアウトしている。手元に設定のファイルがあり、未コミットの変更がある。コミット済みの中身が、既定のブランチのものと同じである。
  利用者が書いたばかりの設定や、コミットしていない直しで、すぐ続けられるようにするためである（ADR 0008 の「直したあとは同じセッションで続けてよい」を残す）。
  既定のブランチの作業ツリーにある未コミットの変更は、利用者のものである。スキルは、課題の変更を、課題のブランチか、スクラッチパッドの作業ツリーでしか行わない。
  3 つ目の条件は、遅れた既定のブランチの古い中身や、push していないコミットの中身を、未コミットの変更と一緒に読まないためである。
- **手元に、読んだものと違うファイルがあるときは、利用者に伝える。** 手元のファイルを使わないことと、効かせるには既定のブランチに入れることを伝える。直したのに効かない、と迷わせないためである。
- **既定のブランチを取れないときは、止まる。** `git fetch origin` の失敗や、ファイルを読むコマンドの失敗を、設定が無いものとして扱わない。設定が無いとするのは、既定のブランチにファイルが無いと確かめられたときだけである。
- **既定のブランチにファイルが無ければ、設定が無いものとして扱う。** 課題のブランチにだけあるファイル（設定のファイルを足す課題）は読まない。値は利用者に確かめる。
- **手元の作業ツリーが既定のブランチでないとき（再開して、課題のブランチになっている、など）は、設定の直しは、既定のブランチに入ってから効く。** 課題のブランチで直しても効かない。正本のファイルと同じ扱いになる。
- **PR が作業するリポジトリの設定のファイルを変えていれば、承認なしではマージしない。** マージすると、あとの課題と、その課題の公開と確認の手順が変わる。承認を受けるときは、設定のファイルの差分も示す。
  変える前か、変えたあとの公開の型が `auto`（か、分からない）なら、マージの承認が公開の承認を兼ねることも、明示して聞く。変える前の型だけを見ると、公開されることを示さないまま、マージで公開されるためである。
- **そのマージのあとは、設定を読み直す。** マージで既定のブランチに入った設定が、公開と確認（8・9 章）から効く。公開の手順を変える課題を、変えたあとの手順で公開するためである。
  `/resolve-issues` では、その回の残りの課題のためにも読み直す。読み直して、レビューする者か `## レビュー` が変わったときは、次のレビューの前に、レビューの設定を確かめ直す（ADR 0008）。
- **対象は、ファイルの全体である。** `## レビュー` に限らない。YAML の値も、ほかの節も、同じ読み方で決まるためである。

## 検討した代替案

- **手元のファイルを読み、PR が設定のファイルを変えていれば、止まって差分を示し、利用者に確かめる（ADR 0012 と同じ形）。** 変えたあとの設定で課題を解決したいときに使える。
  しかし、設定のファイルが決めることは多く（レビューする者、送る範囲、確認のコマンド、マージの方法、公開の型、確かめる操作）、「この差分のまま進めてよいか」の答えが何を許したのかがあいまいになる。答えの記録と、変わったときの聞き直しも要る。
  設定を変える課題は、変える前の設定で解決できる。聞かずに済むほうを採る。
- **再開のときだけ、既定のブランチから読む。** 上の Context の 1 は防げるが、2 と 3 が残る。読む場所の決まりが、新しい着手と再開とで分かれる。
- **いつも既定のブランチから読む（未コミットの変更も読まない）。** 決まりは1つになるが、設定を書いたばかりのリポジトリや、着手の前に止まって設定を直したときに、PR を出してマージするまで続けられない。
- **対象を `## レビュー` に限る。** 外へ送る範囲は守れるが、`review.by` を `none` に変える、`## 毎回確かめること` から行を消す、などの変更が、マージの前に効く。

## Consequences

- 設定のファイルを変えても、既定のブランチに入るまで、スキルの動きは変わらない（既定のブランチの作業ツリーで、未コミットのまま試すときを除く）。
- 手元の既定のブランチにコミットしたが、まだ push していない設定の変更は、読まれない。push して既定のブランチに入れる。
- 設定のファイルを変える PR は、マージの直前に、いつも承認を求められる。
- 設定のファイルを足す課題を再開すると、値を利用者に確かめる。
- Codex に送る範囲を絞る変更も、既定のブランチに入るまで効かない。外に出せないファイルを足す課題では、範囲を絞る変更を、先に既定のブランチに入れる。
- オフラインのときなど、既定のブランチを取れなければ、スキルは設定を読めずに止まる。
- 隣のフォルダーの clone が古くても、新しい設定が読まれる。スキルは、設定を読む前に、そのリポジトリで `git fetch origin` を動かす。
- 設定のファイルの書式の番号と、コメントの印は変えない。
