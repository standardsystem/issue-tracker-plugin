# 課題をまとめて解決する

このスキルの版: 0.7.0

引数は、課題キーを空白かカンマで区切って並べたもの（例: `PROJ-12 PROJ-15`）。無ければ、候補を出して利用者に選んでもらう: `$ARGUMENTS`

1件ごとの手順は `${CLAUDE_PLUGIN_ROOT}/skills/resolve-issue/SKILL.md`（以下 resolve-issue）に従う。最初に全文を読む。
このスキルで決めるのは、複数件を扱うときのことだけである: 対象の選び方、順番、止めた課題の扱い、最後のまとめ。
1回で扱うのは、利用者の指示が無ければ 5 件までとする。

## いつも守ること

- resolve-issue の「いつも守ること」を、課題ごとにそのまま守る。
  そのうち 5（書き込みのツールに `model` を渡す）は、4 章で課題を作るときなど、課題ごとの手順の外の書き込みにも当てる。
- **まとめて任せてもらわない。** 「マージ・公開まで任せる」と言われても、マージや公開の承認にしない。
- **3 章では待たずに次へ進む。** 3 章で、resolve-issue で利用者に聞くか、承認を受ける場面に来たら、その場では聞かない。下の表のとおりに課題を止めて次の課題へ進み、4 章でまとめて聞く。
  着手の前の 1・2 章（対象、順番、作業するリポジトリの場所、公開の型）は、その場で聞いてよい。

| 場面 | すること |
| --- | --- |
| 着手の前か続ける前（resolve-issue の 1 章で、着手しない・利用者に聞く、に当たった。2 章の初めか、再開・4 章で続ける前に、ほかのセッションの予約があって予約できなかった） | 印を残さずに外し、理由を控える（4 章の結果は「外した（ほかのセッションが予約）」など） |
| マージの承認が要る（resolve-issue の 7.4 の条件を欠いた） | `止まった`（マージの承認）を残す。PR は開いたまま |
| 公開について聞くか承認を受ける（resolve-issue の 8 章で `確認待ち`（公開）を残す場面: `manual` の公開、公開が要らないことの確認、公開の仕方が分からない） | 状態をマージ済みにし、`確認待ち`（残っている段階: 公開）を残す |
| 公開の型が `release` | 状態をマージ済みにし、`リリース待ち` を残す |
| 本番での確認を利用者に頼む | 状態をマージ済みにし、`確認待ち`（残っている段階: 本番での確認）を残す |
| そのほか、利用者の答えが要る（`## 毎回確かめること`、範囲の外の変更、3回目以降のレビューで止まった、CI が直らない、マージで衝突した、など） | `止まった` を残す |

## 0. 準備する

resolve-issue の 0 章の 1〜3（MCP、版、設定）を、最初に1回だけ行う。
0 章の 5（設定が無いとき）も、ここで1回だけ行う。設定が無ければ、プロジェクトキーを利用者に聞く。0 章の 6（作業するリポジトリ）は 1 章で、7（公開の型）は 2 章で、課題ごとに決める。

## 1. 対象を決める

**引数があるとき:** 課題ごとに `get_issue` と `list_comments` で読む。課題のプロジェクトキーが設定の `project.key`（設定が無ければ、聞いたプロジェクトキー）と違えば、何も変えずに外す。残りを resolve-issue の 1 章の表に当てる。

- 「2 章へ」に当たる課題を、新しく着手する対象にする。
- 再開の表へ進む課題（最新の印が `確認待ち`・`リリース待ち`・`止まった`）は、「確認を再開できる課題」として分けて示す（下の「確認を再開できる課題の扱い」）。
- ほかは外し、理由を控える（4 章で報告する）。ただし、未完了の先行課題が同じ一覧の中にあるだけなら外さない（2 章の順番で扱う）。

**引数が無いとき:** `list_issues`（`projectKey` は設定の `project.key`。設定が無ければ聞いたプロジェクトキー。`closed: false`、`hasOpenPredecessors: false`、`fields: ["summary", "status", "priority", "assignee", "category", "startDate", "description"]`、`count: 50`）で、着手できる課題を取る。`total` が 50 を超えれば、`offset` で続きを取るか、絞り込みを利用者に聞く。
`fields` は、結果を小さくするために、下の分け方と候補の表に要る項目だけを取る指定である。`description` は本文の先頭（200 文字まで）だけが返る。先頭だけで分けられない課題は、`get_issue` で全文を読む。選んだ課題は、着手の前に 3 章で `get_issue` で全文を読む。
`list_issues` には着手の予約が出ないので、ほかのセッションが予約している課題も候補に入りうる。それは 3 章の着手の直前の確認と予約で外れる。
課題ごとに `list_comments` で最新の印を見て、次のように分ける。

- **確認を再開できる課題:** 最新の印が `確認待ち`・`リリース待ち`・`止まった`。新しく着手する候補には混ぜない。
- **候補にしない課題:** resolve-issue の 1 章で「2 章へ」以外になる課題、実際に触る・スマホで試すなど利用者にしかできない確認が中心の課題、開始日がまだ先の課題。
- **新しく着手する候補:** 残りの課題。

候補を優先度の高い順に並べ、課題キー、件名、カテゴリー、優先度、ひとこと（何をするか）を表で示し、利用者に選んでもらう。確認を再開できる課題は、最新の印と待っていることを添えて別の表で示す。
`AskUserQuestion` の選択肢は 4 つまでなので、候補が 5 件以上なら、表を本文に書いて課題キーで答えてもらう。

**確認を再開できる課題の扱い:** 利用者が続けると選んだ課題を、印で分ける。

- `確認待ち`（残っている段階: 本番での確認）・`リリース待ち`: 3 章で、resolve-issue の再開の表のとおりに続ける。
- `止まった`・`確認待ち`（残っている段階: 公開）: 答えか承認が要るので、3 章では扱わない。4 章で求める対象に入れる。

作業中の印（`着手`・`PR を作成`・`レビュー n 回目`・`マージ`）の課題は、前のセッションが途中で終わったものかもしれない。外したうえで 4 章で報告し、続きは `/resolve-issue` で再開するよう案内する。

## 2. 順番を決める

1. 一覧の中に先行課題と後続課題があれば、先行課題を先にする。後続課題は、先行課題が完了になってから着手する。先行課題が完了にならずに終わったら（止めた、確認待ち、リリース待ち）、後続課題も外す。
2. 同じリポジトリの課題は続けて行う。ブランチは毎回、最新の origin/main から切る。前の課題の PR がマージ前で、同じファイルを触ることになるなら、その課題はあとに回す。前の課題がマージされずに終わったら、あとに回した課題は外して 4 章で報告する。
3. ほかは、優先度の高い順にする。

決めた順番を利用者に一覧で示してから始める。公開の型が分からないリポジトリがあれば、このときにまとめて聞く（resolve-issue の 0 章の 7）。

## 3. 1件ずつ解決する

- 課題ごとに、resolve-issue の 1〜9 章を行う。1 章の確認は、着手する直前に `get_issue` で課題を読み直してから、もう一度行う（状況が変わっていることがある）。
  引数なしで選んだ課題は、`list_issues` で本文の先頭しか読んでいないので、ここで本文の全文と課題の `url` を得る。
- 新しく着手する課題の作業ツリーは、利用者の作業ツリーがきれいでも、課題ごとにスクラッチパッドに別に作る（resolve-issue の 2 章の「きれいでなければ」の手順）。課題を並べて進めるためである。再開する課題は、resolve-issue の再開の表の前置きのとおりに、今ある作業ツリーを探して使う。
- 着手の予約は、resolve-issue の「着手の予約」のとおりに、課題ごとに取り、延ばし、解除する。表のとおりに課題を止めて次へ進むときも、印を残したあとで解除する。4 章で続けるときは、再開と同じく予約し直す。
- レビューは数分かかる。バックグラウンドで動かしている間に、次の課題の 1〜3 章を進めてよい。同時に進める課題は 2 件までとする。
- 先の課題がマージされると、同じリポジトリのあとの課題の PR が衝突することがある。衝突したら、main を取り込んで自分で解消せず、`止まった` を残して次へ進む（resolve-issue の 7.5）。
- 範囲の外で見つけた問題は書き留め、課題にするかは 4 章でまとめて聞く。
- 1件終わるか止めるごとに、利用者に1〜2行で知らせる（課題、PR、レビューの回数、結果）。答えは求めない。

## 4. まとめて、承認と判断を求める

すべての課題を終えるか止めたら、次の順に短く書く。

1. **結果の表:** 課題（`url`）、結果、PR、レビューの回数、残ったこと。結果は次のどれか。
   - 完了
   - マージの承認待ち（PR と head のコミット、欠けた条件）
   - 確認待ち（公開、または本番での確認）
   - リリース待ち
   - 止まった（理由）
   - 外した（理由）
2. **利用者に求めること:** マージの承認、公開の承認、止まった課題の判断、利用者にしかできない確認、範囲の外の問題を課題にするか。答えが要るものは `AskUserQuestion` で聞く。
   承認は課題ごとに、resolve-issue のいつも守ること 1 のとおりに、何をするかと何が起きるかを示して受ける。1つの返事で複数の課題を承認してもらってよいが、承認は示したコミットに対してだけ有効である。
   同じリポジトリに、マージに進みうる課題（マージの承認待ち、`止まった`）が残っているときは、公開の承認はそれらを終えたあとで求める。マージで origin/main が変わり、公開するコミットが変わるためである。
3. **承認や答えを受けた課題を続ける:** resolve-issue の再開の表のとおりに、課題ごとに続ける（7 章なら 7.1 から）。
   同じリポジトリでは、承認を受けたマージをすべて終えてから、公開するコミットを決め直し、公開の承認を受ける。
   また承認や判断が要るところに来たら、同じように止め、この章をもう一度行う。
4. **次の候補:** 今回で着手できるようになった後続課題があれば、挙げる。

利用者が答えずに終わった課題は、印を残したままにする。`止まった`・`確認待ち`・`リリース待ち` の課題は、次に `/resolve-issue` か `/resolve-issues` を呼べば、印から続きを再開できる。
