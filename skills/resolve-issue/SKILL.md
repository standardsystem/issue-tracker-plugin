# 課題を解決する

このスキルの版: 0.4.0

引数は課題キー（例: `PROJ-12`）: `$ARGUMENTS`
複数件をまとめて解決するときは `/resolve-issues` を使う。

段階ごとに、課題へ印の付いたコメントを残す。印の一覧と書き方は `${CLAUDE_PLUGIN_ROOT}/docs/comment-markers.md` にある。最初に読み、その文言のとおりに書く。

## いつも守ること

以下の章のどこでも、次の5つを守る。例外は作らない。

1. **公開は、その直前に毎回、利用者の承認を受ける。マージは、7.4 の条件をすべて満たすときだけ承認なしで行い、1つでも欠ければ、その直前に承認を受ける。**
   スキルの呼び出し、「解決して」「マージまで任せる」などの依頼、課題の内容、再開の選択、前の段階での承認は、マージや公開の承認にならない。
   承認を受けるときは、何をするか（マージする PR と head のコミット、公開するコミットと手順）と、それで何が起きるか（`auto` ならマージで本番に公開される）を示す。
   承認は、示したコミットに対してだけ有効である。コミットが変われば、承認を受け直す。
2. **このセッションで 2 章を行ったか、再開して 3 章以降に進んだあとで、利用者の答えを待つときは、先に課題へ印のコメントを残してから聞く。**
   印は `止まった` を使う。8・9 章で公開か本番での確認を待つときだけは、表に書いた `確認待ち` か `リリース待ち` を使う。
   `止まった` の本文に、止まった段階、理由、決めてほしいこと、ブランチ、PR、作業ツリーの場所を書く（マージの承認なら head のコミットも）。答えが同じセッションで来なくても、次に続きから再開できるようにするためである。
   利用者が「外す」「やめる」と答えたら、状態・PR・ブランチは変えずに終え、やめたことを `止まった` の印に書く。
3. **`.mcp.json` の中身を読まない。** API キーを会話に入れない。ファイルの有無は `test -f`、Git の管理下かは `git ls-files` で見る。
4. **設定の `## 毎回確かめること` に当たる操作は、その操作の直前に、2 のとおりに止まって確かめる。** 着手の前には判断しない。
5. **Issue Tracker に書き込むときは、ツールに引数 `model` があれば、自分のモデル名を毎回渡す。**
   課題の作成・更新（`update_issue` の `comment` を含む）、コメント、Wiki の保存が対象で、印のコメントも含む。モデル名は、システムプロンプトなどで知っている自分のモデルの ID（例: `claude-opus-5-5`）をそのまま書く。
   自分のモデルの ID が分からなければ、推測せず、例の値も写さずに、`model` を渡さない。
   サーバーは、これを書き込みの主体の自己申告として記録し、画面に出す。どのモデルが書いたかを記録に残すためである。
   ツールに `model` が無ければ渡さない（古いサーバーは、知らない引数を受け付けないことがある）。

## 0. 準備する

上から順に行う。

1. **MCP を確かめる。**
   - `.mcp.json` があれば、先に `git ls-files .mcp.json` で Git の管理下かを見る。
     - 管理下なら、「`.mcp.json` は Git に入っている。キーを書いたことがあれば履歴に残っているので、そのキーを無効にして発行し直す」と伝える。
     - 管理下でなければ、`git check-ignore -q .mcp.json` で無視されているかを見る。無視されていなければ、`.gitignore` に足すよう伝える。
   - MCP サーバー `issue-tracker` のツール（`get_issue`、`update_issue`、`add_comment` など）が使えなければ、止める。
     利用者には、次のように設定し、Claude Code を起動し直すよう伝える。設定は利用者が自分の端末で行い、API キーを会話に貼らない。
     API キーは Issue Tracker の画面の「API キー / MCP」で、そのプロジェクトに範囲を絞って発行する。
     - `.mcp.json` が Git の管理下でなければ、`.mcp.json` に次のように書き、`.gitignore` に `.mcp.json` を足す。

       ```json
       {
         "mcpServers": {
           "issue-tracker": {
             "type": "http",
             "url": "https://<Issue Tracker のオリジン>/api/mcp",
             "headers": { "Authorization": "Bearer <API キー>" }
           }
         }
       }
       ```

     - 管理下なら、キーをそこに書かない。代わりに、リポジトリの外に保存される `claude mcp add --transport http --scope local issue-tracker https://<Issue Tracker のオリジン>/api/mcp --header "Authorization: Bearer <API キー>"` を使う。
       このコマンドはキーがシェルの履歴に残るので、打ったあとで履歴から消すよう添える。

2. **版を確かめる。** MCP サーバー `issue-tracker` の instructions に「issue-tracker プラグインのスキルは、版 X.Y.Z 以上で使ってください。」とあれば、このスキルの版（冒頭の「このスキルの版」）と比べる。
   このスキルの版が古ければ、利用者に更新（`/plugin marketplace update issue-tracker-plugin` のあと `/reload-plugins`）を勧め、続けるかを聞く。instructions に版が書いてなければ、比べない。
3. **設定を読む。** `${CLAUDE_PLUGIN_ROOT}/docs/issue-workflow-format.md` を読み、その「スキルの読み方」の 1・2・5 のとおりに、今のリポジトリの `.agents/issue-workflow.md`（と、`definedIn` があれば正本）を読み、`format` の番号を確かめる。
4. **課題を決めて読む。**
   - 引数が無ければ、`list_issues`（`projectKey` は設定の `project.key`、`closed: false`、`hasOpenPredecessors: false`、`count: 100`）で候補を出して、利用者に選んでもらう。`total` が 100 を超えれば、`offset` で続きを取るか、絞り込みを利用者に聞く。設定が無ければ、プロジェクトキーを利用者に聞く。
   - `get_issue` で課題を読む。課題のプロジェクトキーと設定の `project.key` が違えば止める。
5. **設定が無いときは、案を作る。** `list_statuses` と `list_categories` から設定の案を作り、利用者に見せて、ファイルを書くかを聞く。
   書かずに進むことを利用者が選んだら、状態の対応（`inProgress`・`merged`・`done`）、`check`、`merge` を利用者に確かめる。`done` は、完了扱いの状態が1つならそれを使う。
6. **作業するリポジトリを決める。** 書式の「スキルの読み方」の 3〜4 のとおりに、課題のカテゴリーからリポジトリを決め、`repo` の値を決める。
   Markdown の節も、書式の「正本の節」のとおりに決める。`## レビュー` は正本のものを読んでから作業するリポジトリのものを読み、食い違えば作業するリポジトリのものを優先する。`## 確認`・`## 公開と確認` は、作業するリポジトリのものだけを使う。
   今と違うリポジトリの設定を読んだら、その `format` も「スキルの読み方」の 5 のとおりに確かめる。
   そのリポジトリの `AGENTS.md`（無ければ `CLAUDE.md`）を読み、そのルールに従う。
7. **公開の型を決める。** `deploy.type` が無いか、書式に無い値なら、main に入ると自動で公開されるかを含めて、公開の仕方を利用者に聞く。答えを、この課題での型として使い、設定に書くことを提案する。
   利用者にも分からなければ、マージで公開されるかもしれないことを 7.4 の承認で示し、8 章では公開の仕方を聞いて `確認待ち`（残っている段階: 公開）で止める。

ここで決めた値を、以下では次のように呼ぶ。

- 状態: 着手（`statuses.inProgress`）、マージ済み（`statuses.merged`。無ければ着手のまま）、完了（`statuses.done`）
- 既定のブランチ: `gh repo view --json defaultBranchRef` で調べる。以下では main と書く。
- 課題の PR: `gh pr list --search '"<課題キー>"' --state all --json number,title,body,headRefName,state,url` で探す。課題キーは引用符で囲む（囲まないと、GitHub の検索がキーを語に分け、ほかの課題の PR にも当たる）。
  返った PR のうち、タイトル・本文・ブランチ名に課題キーがそのまま含まれる（直後に数字が続かない。`PROJ-1` は `PROJ-12` に当たらない）ものだけを使う。

## 1. 着手できるかを確かめる

`list_comments` で最新の印を探し、課題の状態と合わせて、次の表で決める。上の行から順に当てはめる。

| 当たること | すること |
| --- | --- |
| 状態が完了扱い（`list_statuses` の `closed`）で、マージ済みではない | 着手しない。「完了」のほか、「対応しない」などで閉じた課題も含む |
| 最新の印が `着手`・`PR を作成`・`レビュー n 回目`・`マージ` | 作業中とみなす。最後のコメントの日時と PR の状態を添えて、続きから再開するか、外すかを利用者に聞く。時間がたっていても自動では再開しない。再開なら、下の再開の表へ。外すなら、コメントも状態も変えずに終える |
| 最新の印が `確認待ち`・`リリース待ち`・`止まった` | 下の再開の表へ |
| 未完了の先行課題がある | 着手しない |
| 最新の印が `完了` で、状態が完了扱いでない | 開き直された課題とみなす。前の回のブランチと PR を添えて、新しく着手してよいかを利用者に聞く（担当者が自分以外なら、そのことも添える）。よければ、下の「課題の内容が…」の行だけを確かめて 2 章へ |
| 印が無く、状態が着手かマージ済み | 人が手で作業しているとみなし、着手しない |
| 印が無く、担当者が自分（`get_myself`）以外 | 着手してよいかを利用者に聞く |
| 同じ課題のブランチや PR がある（課題の PR、`git branch -a`） | 見つけたものと PR の状態を利用者に見せ、着手してよいかを聞く |
| 課題の内容が、方針を決めることなど、利用者の決定そのもので、決まらなければ何も作れない | 着手しない。決めてほしいことを利用者に伝える（`## 毎回確かめること` に当たる操作は、ここでは判断しない） |
| どれにも当たらない | 2 章へ |

### 再開の表

再開のときは 2 章を行わない（状態を着手に戻さない、新しいブランチを切らない、`着手` の印を残さない）。
ブランチは `着手` の印の本文、PR は課題の PR（0 章）、作業ツリーは `git worktree list` で探す。
3〜7 章へ再開するときは、作業する場所を次のように決める。`git switch` で利用者の作業ツリーのブランチを変えない。

- `git worktree list` で、課題のブランチをチェックアウトしている作業ツリーを探す（`着手` の印に書いた場所と違うこともある）。
- 見つかり、未コミットの変更（ステージ済み・untracked を含む）が無ければ、そこで続ける。
- 見つかり、未コミットの変更があれば、触らない。前のセッションの続きの変更だと利用者が答えたら、そこで続ける。そうでなければ、利用者がコミットか退避をするまで止まる。
- 見つからなければ、`git fetch origin` のあと、スクラッチパッドに `git worktree add <パス> <ブランチ>` で別の作業ツリーを作る。
- `git worktree add --force` は使わない（同じブランチを2か所で開くと、片方の変更が他方に逆向きの差分として現れる）。

| 最新の印 | 再開する段階 |
| --- | --- |
| `着手` | 3 |
| `PR を作成` | 5（1回目） |
| `レビュー n 回目` | その回の PR のコメントを読み、6 章の最後の表のとおりに次の段階を決める |
| `マージ` | 8 |
| `確認待ち`（残っている段階: 公開） | 8。公開するのは、いつも守ること 1 の承認を受けたときだけ |
| `確認待ち`（残っている段階: 本番での確認） | 9。型が `external` なら、先にその変更が審査を通って公開されたことを利用者に確かめる。確かめられなければ止めたままにする。印に書いた確かめることのうち、利用者が確かめたと答えたものは、確かめたものとして扱う |
| `リリース待ち` | 該当するリリースが出たことを確かめてから 9（タグや GitHub の Releases で確かめる。分からなければ利用者に聞く） |
| `止まった` | 本文の「決めてほしいこと」への利用者の答えを確かめてから、本文の段階。答えが無ければ聞く。本文に利用者がやめたとあれば、続きから再開するかを聞く。7 章なら 7.1 からやり直す。ただし、7.5 の衝突の解消を認められたときは、7.5 のとおりに解消を push して 5 章へ |

## 2. 着手して、ブランチを切る

1. `git status` で、作業ツリーに未コミットの変更（untracked を含む）が無いかを確かめる。
2. `git fetch origin` で、origin/main を最新にする。
3. ブランチを切る。名前は `feat/`・`fix/`・`chore/`・`docs/` のどれかの後に課題キーを入れる（例: `fix/PROJ-12-sort-order`）。リポジトリに決まりがあれば、それに従ったうえで課題キーを入れる。同じ名前のブランチがローカルか origin にあれば、末尾に `-2` などを付ける。
   - 作業ツリーがきれいなら、今のブランチの名前を控えてから、`git switch -c <ブランチ> --no-track origin/main`。控えた名前は `着手` の印に書く。
   - きれいでなければ、理由を問わず、その変更に触らない。スクラッチパッドに `git worktree add --no-track -b <ブランチ> <パス> origin/main` で別の作業ツリーを作り、3〜7 章はそこで行う。
4. `update_issue` で、状態を着手にし、同じ呼び出しの `comment` に `着手` の印のコメント（ブランチ名、作業ツリーの場所、元のブランチ）を書く。

## 3. 対応して、確かめる

- 課題の「やること」と、関連する仕様を読んでから直す。範囲の外の変更は入れない。範囲の外の変更が要るとわかったら、いつも守ること 2 のとおりに止まって確かめる。
- テストを足すか、直す。
- 設定の `check` を通す。設定の `## 確認` に当たる変更なら、そこに書いてあることもする。
- 確かめられなかったこと（本番でしか動かない機能など）は、書き留めておく。

## 4. コミット、push、PR

- 変更したファイルを名前で `git add` する（`git add -A` や `git add .` は使わない）。`.mcp.json`・`.env` など、秘密情報を含みうるファイルは入れない。
- コミットは Conventional Commits の形にし、本文に `Refs: <課題キー>` を書く。
- PR の本文: 目的、変更、確認したこと（コマンドと結果）、未確認のこと、課題キー。
- 課題に `PR を作成` の印のコメントを残す（PR の URL と、PR を作ったときの head のコミット）。
- push は、いつも `git push -u origin <ブランチ>` の形で行う（6・7 章も同じ）。main への push（`HEAD:main`、`origin main` など）はしない。
  `--no-track` で切ったのは、追跡先が origin/main になって、引数なしの `git push` が main に届くのを防ぐためである。
- 以降、このブランチに push したコミットは、必ず PR のコメントに書く（6 章のレビューのコメント、7 章の CI の修正のコメント）。7 章で、head までのコミットがすべて自分の push かを確かめるためである。

## 5. レビューさせる

設定の `review.by` で分ける。依頼文は [references/review-request.md](references/review-request.md) の型で書く。

レビューする者には、PR の head を取り出した使い捨ての作業ツリーを渡す（スクラッチパッドに `git worktree add --detach <パス> <head のコミット>`）。利用者の作業ツリーでは動かさない。終わったら `git worktree remove --force <パス>` で外す。

- **`claude`（既定）:** 別のエージェントを起動し、依頼文を渡す。
- **`codex`:** 設定の `## レビュー`（正本のものを含む。0 章 6）に呼び方が書いてあれば、それに従う。書いてなければ、依頼文をファイルに書き、`codex exec -C <作業ツリー> -s workspace-write -o <結果のファイル> - < <依頼文のファイル>` で動かす。数分かかるので、バックグラウンドで動かす。
- **`none`:** レビューを飛ばして 7 章へ進む。PR にその旨をコメントする。

レビューする者が、head の不一致を報告した、失敗した、結果を返さなかったときは、指摘 0 件として扱わない。回数に数えずに1回だけやり直し、それでも得られなければ、いつも守ること 2 のとおりに止まる。決めてほしいことは「もう一度試す（5 章へ）」「レビュー無しで 7 章へ進む」「やめる」のどれか。

## 6. 指摘を仕分けて、対応する

指摘を鵜呑みにしない。コードと仕様を読んで確かめてから、指摘ごとに次のどちらかに決める。

| 仕分け | 対応 |
| --- | --- |
| 正しい | P0〜P2 は直す。P3 は直さなくてよい |
| 正しくない（誤り、仕様と矛盾、範囲の外） | 直さず、理由を書く。範囲の外でも必要なものは書き留めておき、課題にするかを、このスキルを終えるときにまとめて利用者に聞く |

- 直したら、`check` を通してからコミットして push する。
- レビューの結果と仕分けを、PR に1回のコメントで投稿する（`gh pr comment <番号> --body-file -`）。
  見出しに、何回目か、レビューした者（Codex なら版も）、対象のコミット、正しいとした指摘の重大度ごとの件数を書く。指摘ごとに「直した（コミット）」か「直さない（理由）」を書く。指摘が無くても、その旨を投稿する。
- 課題に `レビュー n 回目` の印のコメントを残す。
- 次の段階は、その回の正しい P0・P1 の件数で決める。

| 回 | 正しい P0・P1 が 0 件 | 正しい P0・P1 が 1 件以上 |
| --- | --- | --- |
| 1・2 回目 | 7 章へ（再レビューしない） | 5 章へ戻る（次の回） |
| 3 回目以降 | 7 章へ | 止まる。決めてほしいことは「もう1回レビューさせる（5 章へ）」「このまま 7 章へ進む」「やめる」のどれか。4 回目以降も、正しい P0・P1 があれば毎回止まる |

## 7. マージする

1. PR の CI が成功したことを確かめる（`gh pr checks <番号> --watch`）。
   - チェックが1つも無ければ、先に `git fetch origin` で origin/main を最新にし、PR の head を取る（7.2 と同じ方法）。そのうえで、リポジトリに CI が無いかを確かめる。次のどれにも当たらなければ、CI が無いとみなす。
     - PR の head か origin/main に `.github/workflows/` のファイルがある（PR がワークフローを消すときも、CI があるとみなす）
     - origin/main のコミットに、チェックかステータスがある（`gh api repos/<owner/repo>/commits/<コミット>/check-runs` と `.../status` の `total_count`）
     - リポジトリの説明（`AGENTS.md` など）に CI がある
   - CI があるのにチェックが無ければ、登録を待ってから 7.1 をやり直す（`gh pr checks` はチェックが無いと待たずに終わる）。数分待っても無ければ、7.4 の条件を欠く。
   - CI が無ければ、その head をスクラッチパッドに `git worktree add --detach <パス> <head>` で取り出し、そこで設定の `check` を通す（終わったら `git worktree remove --force <パス>` で外す）。通した head と結果を PR にコメントする。
     通らなければ、CI の失敗と同じように直す。
   - 失敗したら、原因を直して `check` を通し、push する。push したコミットと直した内容を PR にコメントし、7.1 をやり直す。
     修正が失敗の原因を超えて動きを変えるとき、または2回直しても失敗するときは、止まる。
2. `git fetch origin` のあと、PR の head を `gh pr view <番号> --json headRefOid` で取る。
3. 最後にレビューを終えたコミット（レビューを1回も終えていなければ、`PR を作成` の印に書いた head）を X として、次を確かめる。どちらかが違えば、止まってそれらのコミットを利用者に見せる。
   - X が head の祖先である（`git merge-base --is-ancestor X <head>`）。
   - `git log X..<head>` のコミットが、すべて PR のコメントに書いた自分の push である。
4. 次の条件をすべて満たせば、承認を受けずに 7.5 へ進む。1つでも欠ければ、いつも守ること 1・2 のとおりに `止まった`（決めてほしいこと: マージの承認。head のコミットと、欠けた条件も書く）を残し、head のコミットを示して承認を受ける。
   - レビューを1回以上終え、最後の回の正しい P0・P1 が 0 件だった（6 章の表で 7 章へ進んだ）。`review.by` が `none` のとき、5 章で「レビュー無しで 7 章へ」を選んだとき、6 章で止まったあと「このまま 7 章へ」を選んだときは欠ける。
   - 7.3 の X のあとのコミットが、最後の回の 6 章で「直した」と PR に書いた修正と、7.1 の CI の修正だけである。ほかの push（main の取り込み、衝突の解消、範囲を足す変更など）があれば欠ける。
   - PR の CI にチェックがあれば、7.1 ですべて成功した。7.1 で CI が無いと確かめたリポジトリでは、7.2 の head と同じ head で設定の `check` を通し、その head と結果を PR にコメントした（7.1）。7.2 の head か origin/main が 7.1 で確かめたときと違えば、7.1 からやり直す。
   - マージしても公開されない。公開の型が `none`・`manual`・`release`・`external` のどれかと確かめられたときだけ満たす。`auto`、型が分からない（0 章の 7 で利用者にも分からなかった）、書式に無い値は欠ける。マージの承認が公開の承認を兼ねるためである。
   - 設定の `## 毎回確かめること` に、このマージが当たらない。作業するリポジトリのファイルと、`definedIn` の正本のファイルの両方を見る。

   再開したときは、レビューの条件を、課題の `レビュー n 回目`・`止まった` の印と PR のコメントで確かめる。確かめられなければ、欠けるものとする。
   `止まった`（マージの承認）から再開して、その本文の head への承認を受けていれば、7.2 の head がそれと同じときは承認を受けたものとして 7.5 へ進む。違えば、承認を受け直す。
5. 設定の `merge` の方法で、7.2 で取った head（承認を受けたなら、その head）に固定してマージする（`gh pr merge <番号> --merge|--squash|--rebase --match-head-commit <head>`）。
   head が変わっていて失敗したら、7.1 からやり直す。衝突で失敗したら、main を取り込んで自分で解消せず、止まって利用者に伝える。解消してよいと答えがあれば、解消を push してから 5 章へ戻り、レビューを受け直す。
6. 課題に `マージ` の印のコメントを残す（マージコミットと、承認を受けたか。受けなければ、7.4 の条件を満たしたこと）。
7. 2 章か再開で別の作業ツリーを作っていれば、`git worktree remove <パス>` で外す（`--force` は付けない）。未コミットの変更があって外せなければ、残したまま利用者に伝える。
   作っていなければ、`着手` の印に書いた元のブランチに戻す（`git switch <ブランチ>`）。

## 8. 公開する

0 章で決めた公開の型で分ける。8・9 章で止めるときは、状態をマージ済みにし、表の印のコメントを残す。

| 型 | すること | 止めるときの印 |
| --- | --- | --- |
| `none` | 9 へ進み、本番の確認をせずに完了にする | — |
| `auto` | 設定の `## 公開と確認` のとおりに、公開の処理が終わるのを待ち、9 へ | 失敗したら `止まった` |
| `manual` | 下のとおりに、承認を受けてから公開して、9 へ | 承認を待つ間は `確認待ち`（残っている段階: 公開） |
| `release` | リリースを出すことはしない | `リリース待ち` |
| `external` | 審査に出すのは利用者である。審査を通ったあとで確かめることを書いて止める | `確認待ち`（残っている段階: 本番での確認） |

- `## 公開と確認` が無いのに、`auto` の待ち方や `manual` の手順が要るときは、利用者に聞く。待つ間は `確認待ち`（残っている段階: 公開）の印を残す。
- `manual` で公開が要らない（文書だけの変更など）と考えたら、その理由を示して利用者に確かめる。認められたら、本番の確認をせずに完了にする。
- `manual` で公開するときは、次のとおりにする。利用者の作業ツリーにある未コミットの変更や、承認していないコミットを本番に混ぜないためである。
  1. `git fetch origin` のあと、`git rev-parse origin/main` で公開するコミットを決める。
  2. そのコミットと、マージコミットのあとに main に入ったコミット（`git log <マージコミット>..<公開するコミット>`）と、手順を示して承認を受ける。
     設定の手順が、取り出した作業ツリーではなくリモートの main などを公開するもの（`git archive origin/main` など）なら、公開するコミットを固定できないことも示す。
  3. スクラッチパッドに `git worktree add --detach <パス> <公開するコミット>` で取り出し、そこで設定の手順を行う。終わったら `git worktree remove --force <パス>` で外す。

## 9. 本番で確かめて、完了にする

- 公開したものを、設定の `## 公開と確認` の確かめ方で本番で確かめる。書いてなければ、確かめ方を利用者に聞く（待つ間は、状態をマージ済みにし、`確認待ち`（残っている段階: 本番での確認））。
- すべて確かめられたら、`update_issue` で状態を完了にし、同じ呼び出しの `comment` に `完了` の印のコメント（確かめたこと。利用者が確かめたものは、そう書く）を書く。
- 自分で確かめられないこと（スマホでの動作、ログインが要る操作など）が残るときは、完了にしない。
  状態をマージ済みにし、`確認待ち`（残っている段階: 本番での確認）の印のコメントに確かめる方法を書いて、利用者に頼む。
- このスキルを終えるとき（完了にしたとき、`確認待ち`・`リリース待ち` で止めたとき）は、6 章で書き留めた範囲の外の指摘があれば、課題にするかを利用者に聞く。
