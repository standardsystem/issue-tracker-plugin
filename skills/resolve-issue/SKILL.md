# 課題を解決する

引数は課題キー（例: `PROJ-12`）: `$ARGUMENTS`

複数件をまとめて解決するときは `/resolve-issues` を使う。

段階ごとに、課題へ印の付いたコメントを残す。印の一覧と書き方は `${CLAUDE_PLUGIN_ROOT}/docs/comment-markers.md` にある。最初に読み、その文言のとおりに書く。

## 0. 準備する

1. **MCP を確かめる。** MCP サーバー `issue-tracker` のツール（`get_issue`、`update_issue`、`add_comment` など）が使えなければ、止める。
   利用者には、リポジトリの `.mcp.json` に次のように設定し、Claude Code を起動し直すよう伝える。
   API キーは Issue Tracker の画面の「API キー / MCP」で、そのプロジェクトに範囲を絞って発行する。`.mcp.json` は Git に入れない（`.gitignore` に足す）。

   ```json
   {
     "mcpServers": {
       "issue-tracker": {
         "type": "http",
         "url": "https://<Issue Tracker のオリジン>/api/mcp",
         "headers": { "Authorization": "Bearer ${ISSUE_TRACKER_API_KEY}" }
       }
     }
   }
   ```

2. **版を確かめる。** このスキルの版は frontmatter の `metadata.version` にある。
   MCP サーバー `issue-tracker` の instructions に「issue-tracker プラグインのスキルは、版 X.Y.Z 以上で使ってください。」とあれば比べる。
   このスキルの版が古ければ、利用者に更新（`/plugin marketplace update issue-tracker-plugin`）を勧め、続けるかを聞く。instructions に版が書いてなければ、比べない。
3. **設定を読む。** `${CLAUDE_PLUGIN_ROOT}/docs/issue-workflow-format.md` を読み、その「スキルの読み方」のとおりに `.agents/issue-workflow.md` を読む。
   - 課題のプロジェクトキーと、設定の `project.key` が違えば止める。
   - 設定のファイルが無ければ、`get_issue` で課題を読み、`list_statuses` と `list_categories` から設定の案を作る。利用者に見せて、ファイルを書くかを聞く。
     書かずに進むことを利用者が選んだら、`check` と `merge` を聞き、公開の型は「分からない」として扱う。
4. **作業するリポジトリを決める。** 課題のカテゴリーから、書式の「スキルの読み方」のとおりに決める。そのリポジトリの `AGENTS.md`（無ければ `CLAUDE.md`）を読み、そのルールに従う。

ここで決めた値を、以下では次のように呼ぶ。

- 状態: 着手（`statuses.inProgress`）、マージ済み（`statuses.merged`）、完了（`statuses.done`）
- 既定のブランチ: `gh repo view --json defaultBranchRef` で調べる。以下では main と書く。

引数が無いときは、`list_issues`（`projectKey`、`closed: false`、`hasOpenPredecessors: false`）で候補を出して、利用者に選んでもらう。

## 1. 課題を読み、着手できるかを確かめる

`get_issue` で課題を読み、`list_comments` で最新の印を探す。次のどれかに当たれば、着手しないで利用者に伝える。

- 未完了の先行課題がある。
- 最新の印が「作業中」の扱い（`着手`・`PR を作成`・`レビュー n 回目`・`マージ`）である。
  最後のコメントの日時と、PR があればその状態を添えて、続きから再開するか外すかを利用者に選んでもらう。時間がたっていても、自動では再開しない。
- 状態が着手なのに印の付いたコメントが無い（人が手で作業しているとみなす）。
- 同じ課題のブランチや PR がすでにあり、上の印で説明がつかない（`gh pr list --search <課題キー>`、`git branch -a`）。
- 課題の内容が、利用者の判断を要する（方針を決める、法務の文面、設定の `## 毎回確かめること` に当たる）。

最新の印が `確認待ち`・`リリース待ち` なら、8 か 9 から再開する。`止まった` なら、利用者の答えを確かめてから、止まった段階から再開する。

## 2. 着手して、ブランチを切る

- 状態を着手にする（`update_issue`）。
- 最新の main からブランチを切る。名前は `feat/…`、`fix/…`、`chore/…`、`docs/…`。
- 作業ツリーに自分のものでない未コミットの変更があれば、触らない。
  スクラッチパッドに `git worktree add -b <ブランチ> <パス> origin/main` で別の作業ツリーを作り、そこで作業する。
- 課題に `着手` の印のコメントを残す。

## 3. 対応して、確かめる

- 課題の「やること」と、関連する仕様を読んでから直す。範囲の外の変更は入れない。
- テストを足すか、直す。
- 設定の `check` を通す。設定の `## 確認` に当たる変更なら、そこに書いてあることもする。
- 確かめられなかったこと（本番でしか動かない機能など）は、書き留めておく。

## 4. コミット、push、PR

- コミットは Conventional Commits の形にし、本文に `Refs: <課題キー>` を書く。
- PR の本文: 目的、変更、確認したこと（コマンドと結果）、未確認のこと、課題キー。
- 課題に `PR を作成` の印のコメントを残す（PR の URL）。

## 5. レビューさせる

設定の `review.by` で分ける。依頼文の型は [references/review-request.md](references/review-request.md) にある。どれでも、結果の投稿は自分で行う。

- **`claude`（既定）:** 別のエージェントを起動し、依頼文を渡す。エージェントにはファイルを変更させず、GitHub にも投稿させない。
- **`codex`:** 設定の `## レビュー` に呼び方が書いてあれば、それに従う。書いてなければ次のとおりにする。
  1. PR の head を、スクラッチパッドの使い捨ての作業ツリーに取り出す（`git worktree add --detach <パス> origin/<ブランチ>`）。Codex はその中だけを書ける状態で動かし、利用者の作業ツリーでは動かさない。
  2. 依頼文をファイルに書き、`codex exec -C <作業ツリー> -s workspace-write -o <結果のファイル> - < <依頼文のファイル>` で動かす。数分かかるので、バックグラウンドで動かす。
  3. 使い終わった作業ツリーを外す（`git worktree remove`）。

  Codex は非対話で動き、GitHub への投稿の承認ができずに失敗するので、投稿させない。
- **`none`:** レビューを飛ばして 7 へ進む。PR にその旨を書く。

結果を読み、指摘を確かめてから（6 の仕分け）、PR にコメントで投稿する（`gh pr comment <番号> --body-file -`）。
見出しに、レビューした者（Codex なら版も）、対象のコミット、重大度ごとの件数を書く。指摘が無くても、その旨を投稿する。
課題に `レビュー n 回目` の印のコメントを残す。

## 6. 指摘に対応して、再レビュー

指摘を鵜呑みにしない。コードと仕様を読んで確かめてから、指摘ごとに次のどれかに決める。

| 仕分け | 対応 |
|---|---|
| 直す（指摘が正しい） | 直してコミットする |
| 直さない（誤り、仕様と矛盾、範囲の外） | 理由を書く。範囲の外でも必要なものは、課題にするかを利用者に確かめる |

- 仕分けの結果を PR にコメントする。指摘ごとに「直した（コミット）」か「直さない（理由）」を書く。
- 直したら push して、5 に戻る。
- **止まる条件:** P0 と P1 が 0 件で、P2 はすべて直したか理由を書いた。P3 は直さなくてよい。
- **3回目のレビューでも P0 か P1 が残ったら、止まる。** 課題に `止まった` の印のコメントを残し、残った指摘と迷っている点を利用者に伝える。

## 7. マージする

- マージは、利用者の承認を受けてから行う。利用者が最初の指示でマージまで任せたときは、承認なしでよい。
- 公開の型が `auto` なら、マージすると公開されることを明示して承認を求める。
- マージの方法は、設定の `merge` に従う（`gh pr merge <番号> --merge`・`--squash`・`--rebase`）。
- 課題に `マージ` の印のコメントを残す（マージコミット）。

## 8. 公開する

設定の `deploy.type` で分ける。

| 型 | すること |
|---|---|
| `none` | 9 へ進み、本番の確認をせずに完了にする |
| `auto` | 設定の `## 公開と確認` のとおりに、公開の処理が終わるのを待つ。失敗したら止めて利用者に伝える |
| `manual` | 公開が要るかを判断して、利用者に伝える。公開は利用者の指示があるときだけ行う。指示が無ければ、`確認待ち` で止める |
| `release` | 状態をマージ済みにする（無ければ着手のまま）。`リリース待ち` の印のコメントを残して止める。リリースを出すことはしない |
| `external` | 状態をマージ済みにする（無ければ着手のまま）。`確認待ち` の印のコメントに、審査のあとで確かめることを書いて止める |
| （書いてない） | 状態をマージ済みにする（無ければ着手のまま）。利用者に公開の仕方を聞き、設定に `deploy.type` を書くことを提案する |

- `manual` で公開するときは、最新の origin/main をスクラッチパッドのきれいな作業ツリーに取り出し、そこで設定の手順を行う。利用者の作業ツリーにある未コミットの変更を、本番に混ぜないためである。
- 設定の `## 毎回確かめること` に当たる公開は、任されていても毎回利用者に確かめる。

## 9. 本番で確かめて、完了にする

- 公開したものを、設定の `## 公開と確認` の確かめ方で本番で確かめる。
- すべて確かめられたら、状態を完了にし、`完了` の印のコメントに確かめたことを書く。
- 自分で確かめられないこと（スマホでの動作、ログインが要る操作など）が残るときは、完了にしない。
  状態をマージ済みにし（無ければ着手のまま）、`確認待ち` の印のコメントに確かめる方法を書いて、利用者に頼む。

## 途中で止まって利用者に確かめるとき

次のときは、課題に `止まった` の印のコメントを残し、利用者に確かめる。

- 仕様の変更が要る。
- 設定の `## 毎回確かめること` に当たる操作をする。
- Codex など外部に送る範囲を広げる。
- 課題の範囲の外の変更が要る。
